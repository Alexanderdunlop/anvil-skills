# File Contract

Every file anvil reads or writes, its purpose, its size budget, and its exact
format. This document is the authority. If a skill and this document disagree,
this document is right and the skill is a bug.

---

## 0. Two trees, and the path rule

There are two directory trees and they must never be confused. Most of the
bugs available in this project come from collapsing them.

**Tree A — what `anvil-skills` ships.** This repo. Authored by hand, versioned,
published to a marketplace.

```
anvil-skills/
├── .claude-plugin/
│   ├── plugin.json
│   └── marketplace.json
├── skills/
│   ├── setup/SKILL.md
│   ├── scope/SKILL.md
│   ├── kickoff/SKILL.md
│   ├── build/SKILL.md
│   ├── verify/SKILL.md
│   ├── review/SKILL.md
│   ├── feedback/SKILL.md
│   └── research/SKILL.md
├── docs/
├── evals/
└── README.md
```

**Tree B — what anvil creates in a user's repo.** Generated by `/setup`,
maintained by `/feedback`, owned by that project.

```
their-project/
└── .anvil/
```

Sections 2 onward of this document describe **Tree B only**. Nothing in Tree B
appears at a repo root — it is all under `.anvil/`. Tree A has no `.anvil/`
requirement at all; see §8 for the separate question of whether this repo keeps
one for dogfooding.

### The path rule

> **Every path to a Tree B file, in every skill, is written
> `${CLAUDE_PROJECT_DIR}/.anvil/...`. Never a bare `.anvil/`.**

This is not style. Marketplace plugins are copied into
`~/.claude/plugins/cache/` rather than run in place, so if this repo ships its
own `.anvil/` for dogfooding, that directory lands on every user's machine. A
bare relative path is then ambiguous between two real `.anvil/` trees on disk,
and a skill can read _this repo's_ `CONFIG.md` instead of the user's.
`${CLAUDE_PROJECT_DIR}` resolves to the user's project root and substitutes
inside skill content wherever it appears, which removes the ambiguity
completely.

A bare `.anvil/` path in any `SKILL.md` is a review-blocking defect.

### Skills, not commands

All eight are `skills/<name>/SKILL.md`. Both `skills/` and `commands/` produce
`/name` shortcuts, but `skills/` is the current form and `commands/` is the
older flat-markdown one. The property anvil needs — invoked by the user,
never auto-fired by the model — comes from frontmatter, not from the directory:

```yaml
---
name: scope
description: Turn a rough idea into a sliced, approved ticket with acceptance criteria.
disable-model-invocation: true
---
```

`disable-model-invocation: true` on all eight. Seven of the eight write files
and two of those sit behind approval gates; the eighth, `/research` (§4.11),
writes nothing but reads the entire feedback history. None should ever fire
because the model thought it seemed relevant.

A `CLAUDE.md` at this repo's root does **not** load as project context for
users. Any guidance anvil wants to ship has to live inside a skill.

### The ticket resolution rule

> **Any skill that needs the ticket body resolves it through `CONFIG.md`'s
> `tracker:` mode. Never by assuming `.anvil/tickets/<id>/TICKET.md` exists.**

Under `tracker: local` that file is the ticket. Under a working external
integration it does not exist at all, and under an external tracker with no
integration it exists only as a labelled mirror that may be stale. A skill that
opens the path directly is correct in one of three modes and silently wrong in
the other two. See §4.8 for the modes.

### When Tree B does not exist

All eight skills install together, so a user can run `/scope` in a repo that has
never seen `/setup`. Every path then resolves to nothing.

> **Any skill that finds no `${CLAUDE_PROJECT_DIR}/.anvil/` stops immediately
> and tells the user to run `/setup`. It does not create files, does not fall
> back to defaults, and does not infer a `CONFIG.md` from what it can see.**

Opportunistic creation is the failure mode worth naming: a skill that helpfully
writes a half-guessed `CONFIG.md` produces a context file nobody authored and
nobody trusts, and `/setup` then has to decide whether to overwrite it. Missing
is a clean state. Half-populated is not.

This is also the reason `/setup` cannot be held back for a private M7. If anvil
is published before M7, a crude `/setup` ships with it — even one that only asks
questions and writes the files verbatim — because seven skills that all refuse
to run is not a release.

## 1. The core principle

A line in a context file is paid every time the command that reads it runs —
forever. So the default answer to "should this go in a context file?" is **no**.

Anvil no longer owns anything read on _every_ run (§4.10) — `CLAUDE.md` in
`/feedback`'s row in §3 is not a counter-example, since it is read by one
command and owned by the repo rather than by anvil. That makes the cost
narrower, not smaller: a line in `process/scope.md` is charged to every future
`/scope`, and a line in `REVIEW_RULES.md` to every future `/verify` and
`/review`. A line nobody ever removes is a bill nobody stops paying, and the
narrower scope only changes whose bill it is.

Three things follow from that, and they are enforced mechanically rather than
left to judgment:

**The admission test.** Nothing enters a context file without passing all three
questions. These are inlined verbatim into `skills/feedback/SKILL.md` so they
fire at the point of decision:

1. Could Claude have inferred this from the code? If yes, drop it.
2. Is it stated as a direct constraint rather than a suggestion? If not,
   rewrite it until it is.
3. Does it fit on one line? If not, it is two lessons or it is not a lesson.

Most corrections fail question 1. They die in the logs. That is the system
working, not failing.

**Scope tiers, narrowest by default.** Cost climbs steeply with tier, so a
lesson is written at the narrowest tier that holds it, and is only promoted on
evidence:

| Tier    | Destination                        | Read when                       | Promotion threshold                        |
| ------- | ---------------------------------- | ------------------------------- | ------------------------------------------ |
| Ticket  | `tickets/<id>/CONTEXT.md`          | once, during that ticket        | n/a — never promoted automatically         |
| Command | `process/<command>.md`             | that command runs               | same fingerprint in **2** distinct tickets |
| Global  | proposed to the repo's `CLAUDE.md` | **every session, anvil or not** | same fingerprint in **3** distinct tickets |

Nothing enters the global tier on first sighting. Ever.

The global tier is not an anvil file. Anvil owns no always-read file — see §4.10
for why the one it used to own was deleted. At three sightings `/feedback`
drafts a one-line addition to the repo's `CLAUDE.md` and the human accepts or
rejects it. `CLAUDE.md` is human-owned; anvil suggests and never writes.

**Budgets are hard, at a number the project sets.** These are two separate
things and it matters that they stay separate:

- _The mechanism is not optional._ A budget is a hard ceiling, not a warning.
  When a file is at its limit, adding a line requires removing one, and
  `/feedback` must name the evicted line and say why the new line beats it. At
  the limit with nothing weaker to drop, `/feedback` fails. None of this is
  configurable.
- _The number is a setting._ Every budget in §4 is a **default**, and a project
  may override any of them in `.anvil/BUDGETS.md` (§4.2).

The mechanism is what makes every addition a ranking decision instead of an
append, and it is what makes pruning happen continuously rather than on a
schedule nobody keeps. Making the number configurable does not weaken that —
the trade still has to be made, at whatever ceiling the project chose. What it
avoids is a document pretending to know how many rules a codebase it has never
seen ought to have.

The rationale a human reads lives in `docs/PHILOSOPHY.md` and the README. Do not
put URLs or reasoning in context files — Claude will not fetch a link mid-run,
so it is pure token cost.

## 2. Directory layout (Tree B)

Every path below is relative to `${CLAUDE_PROJECT_DIR}`.

```
${CLAUDE_PROJECT_DIR}/.anvil/
  CONFIG.md                    anvil's config + pointers outside the repo
  BUDGETS.md                   optional line-budget overrides; /feedback only
  CRITICAL_PATHS.md            what must not break, and how to check
  REVIEW_RULES.md              what to look for in a diff; /verify + /review only
  process/
    scope.md                   corrections scoped to /scope
    kickoff.md                 corrections scoped to /kickoff
    build.md                   corrections scoped to /build
    verify.md                  corrections scoped to /verify
    review.md                  corrections scoped to /review
  feedback/
    human.jsonl                append-only, corrections a person made
    self.jsonl                 append-only, stalls the model observed itself
    unrouted.md                corrections /feedback could not route
  tickets/
    0007-add-auth-guard/
      TICKET.md                /scope output, approval gated — see §4.8
      CONTEXT.md               /kickoff output
      PLAN.md                  /kickoff output
      TEST_CASES.md            /kickoff output
      VERIFY.md                /verify output, read by humans only
```

`.anvil/` is committed to git. Feedback compounds across the team, and a
bloated context file shows up as PR noise, which is a feature.

## 3. Read budget per run

There are two taxes, measured two different ways.

**Tree A tax — what the plugin itself costs.** Measured with
`claude plugin details anvil-skills`, which prints the component inventory and
projected token cost split into always-on and on-invoke. Always-on is the
number that matters: it is paid in every session whether anvil is used or not.
Target is **zero** always-on beyond skill descriptions —
`disable-model-invocation: true` plus keeping all substance inside the skill
body should get there. This is a better check than counting lines, because it
measures what the model is actually charged.

**Tree B tax — what a project's `.anvil/` costs.** Measured with `wc -l`, per
the budgets in §4 — or per this project's overrides in `BUDGETS.md` (§4.2),
which is why the numbers below are the shipped defaults rather than facts. The point is the total below, not the individual file.

| Command     | Files read                                                             | Lines      |
| ----------- | ---------------------------------------------------------------------- | ---------- |
| `/scope`    | CONFIG + process/scope                                                 | 30         |
| `/kickoff`  | CONFIG + process/kickoff + ticket body                                 | 70         |
| `/build`    | CONFIG + process/build + CONTEXT + PLAN + TEST_CASES                   | 170        |
| `/verify`   | CONFIG + process/verify + REVIEW_RULES + CRITICAL_PATHS + TEST_CASES   | 140        |
| `/review`   | CONFIG + process/review + REVIEW_RULES + ticket body + PLAN + the diff | 160 + diff |
| `/feedback` | all context files + BUDGETS + both feedback logs + `CLAUDE.md`         | 180 + logs |
| `/research` | unrouted + both feedback logs                                          | 0 + logs   |

Every row dropped by 30–40 lines when `RULES.md` was deleted (§4.10). `/scope`,
the command run most often and most casually, now costs 30 lines.

`REVIEW_RULES.md` appears in exactly two rows. It is invisible to `/scope`,
`/kickoff` and `/build`, which is the entire reason it is a separate file from
the one it replaced.

`BUDGETS.md` appears in exactly one, for the same reason taken further — see
§4.2. Numbers only `/feedback` acts on should be readable only by `/feedback`.

`/feedback` is the only command that reads everything, because it is the only
command that writes to context files.

**`CLAUDE.md` in `/feedback`'s row is read for the duplication check only** —
trigger 2 of the staleness pass (§6), which removes an anvil-side line whose
substance now appears in `CLAUDE.md`. It carries no budget here because it is
not an anvil file and its size is not anvil's to control. `/feedback` reads it
and **never** writes it; the `claude-md` category (§5) proposes, and a human
edits.

`/research` (§4.11) reads no context file at all. Its inputs are `unrouted.md`
and the two logs, none of which is budgeted, so its context-file cost is zero.

**Confirmed: the write-only artifacts cost nothing.** `VERIFY.md` (§4.9) and
the two feedback logs (§4.6) are absent from every row above, and that is
correct. `VERIFY.md` is read by no skill at all — it is for human reviewers.
`human.jsonl` and `self.jsonl` are read only by `/feedback` and `/research`, and
both of those read both files. Neither is read at runtime by `/scope`,
`/kickoff`, `/build`, `/verify` or `/review`, so neither has a budget and
neither affects the numbers in this table. This is why they are allowed to grow
without limit while context files are not.

`ticket body` resolves per `CONFIG.md`'s `tracker:` mode — see §4.8. Its cost is
roughly the same in all three modes; only its location changes.

## 4. File specifications

### The seeding rule

> **Anvil may seed a file from what the user tells it. Never from what anvil
> assumes.**

This is why `/setup` populates some files and not others, and the line is not
arbitrary:

| File                | Seeded? | Because                                                    |
| ------------------- | ------- | ---------------------------------------------------------- |
| `CONFIG.md`         | yes     | the user answers where the tracker and design system are   |
| `CRITICAL_PATHS.md` | yes     | the user names what must not break                         |
| `REVIEW_RULES.md`   | yes     | the user says what they want looked for in a diff          |
| `BUDGETS.md`        | n/a     | absent means defaults; the user writes it only to override |
| `process/*.md`      | **no**  | anvil would be guessing — see §4.5                         |

Every seeded line above originates with a human who knows this repo. A
`process/*.md` seed would originate with anvil predicting what this repo will
get wrong, which is a different thing wearing the same clothes.

---

### 4.1 `.anvil/CONFIG.md`

**Purpose.** Anvil's own configuration, plus pointers to things that live
_outside_ the repo and cannot be found by reading it. Nothing else.

The name matters. This file was called `MAP.md`, and the name was an invitation:
a map of the repo is a thing you fill with repo facts, and it filled with
`test:`, `build:`, `lint:` and `entrypoint:`. Every one of those failed the
admission test in §1 — all four are readable from `package.json` or its
equivalent, so they are precisely the "could Claude have inferred this" case.
They were also worse than useless. A lookup that goes stale gets re-run; a
_line_ that goes stale is trusted, and Claude will run `pnpm test` long after
the repo moved to `bun test`. `CONFIG.md` does not invite that content.

**Budget.** 10 lines. Default — see §4.2.

**Written by.** `/setup`, then `/feedback` for category `config`.

**Format.** `key: value`, one per line. No prose, no headings beyond the title.
Unknown values are omitted, not left blank.

```markdown
# Config

tracker: jira PROJ
tickets: .anvil/tickets/
design: figma.com/file/abc123
smoke: mcp:playwright
```

Nothing beyond this shape. Four keys is typical and 10 lines is the ceiling.

**Explicit exclusion: build, test and lint commands do not belong here.** Nor do
entry points, directory layouts, or framework names. If a command is genuinely
undiscoverable — an internal wrapper with no manifest entry, say — that is a
`CLAUDE.md` fact, where it is stated once and read by every tool, not a
`CONFIG.md` fact duplicated inside anvil.

The keys earn their place by pointing somewhere anvil cannot look: `tracker` at
an external backlog, `design` at a Figma file, `smoke` at an MCP server.
`tickets` is the exception, and it is there because it is anvil's own
configuration rather than a repo fact.

`tracker: local` means `/scope` mints ticket IDs itself, as `max(existing) + 1`.
Any other value names an external tracker and `/scope` asks for the ID instead
of inventing one.

**Known limitation of `tracker: local`.** `max(existing) + 1` collides across
git worktrees: two worktrees off the same repo both see the same highest number
and both mint it. Not urgent, and not worth a counter file — a counter file
collides the same way and adds corruptible state. If worktrees become a
`/kickoff` option, the fix is to switch that repo to `tracker:` pointing at
something with real ids, or to seed the slug with a short branch prefix.
Recorded here so it is a known cost rather than a surprise.

`smoke: none` is valid and `/verify` must degrade gracefully to a manual
checklist when it is set.

### 4.2 `.anvil/BUDGETS.md`

**Purpose.** Per-project overrides for the numbers anvil ships as defaults: the
line budgets in §4, and the staleness threshold in §6. Optional — a repo with no
`BUDGETS.md` uses the shipped defaults, which is the expected case.

**Read by.** `/feedback` only.

**Written by.** Humans only. `/feedback` reads this file and **never** writes
it. See §6 step 4.

**Budget.** None, and it has no runtime cost.

**Format.** `key: number`, one per line. Any key not listed uses its default.

```markdown
# Budgets

critical_paths: 60
review_rules: 45
process:scope: 40
stale_after: 8
```

Keys: `config`, `critical_paths`, `review_rules`, `process`, `process:<command>`,
`ticket`, `context`, `plan`, `test_cases`, `stale_after`.

**`stale_after`.** The only key that is not a line count. It is the number of
tickets after which a promoted line whose fingerprint has gone quiet is
presented for review — §6, trigger 3. Default **20**.

It belongs in this file rather than in the skill for exactly the reason §4.5
gives for not seeding `process/*.md`: 20 is a shipped guess about a repo anvil
has never seen. It is a guess with a much smaller blast radius than a seeded
line, because getting it wrong delays or hastens a _question_ rather than
installing a constraint — but it still shapes behaviour in every repo, and a
shipped guess that shapes behaviour is a thing a project must be able to
override. A repo shipping several tickets a week wants its question after five,
not after twenty; a repo shipping one a month wants the opposite. Neither
number is knowable from here.

It is here and not in `CONFIG.md` for the reason set out below: only
`/feedback` acts on it, so only `/feedback` should pay to read it.

**`process` and `process:<command>`.** `process` sets the ceiling for all five
`process/*.md` at once. `process:<command>` overrides one of them, and takes
precedence:

```markdown
process: 30 # kickoff, build, verify, review → 30
process:scope: 40 # scope → 40, not 30
```

Resolution order for a `process/*.md` file is `process:<command>`, then
`process`, then the §4.5 default of 20. The two-level shape exists because
`/scope` accumulating more corrections than `/build` is the expected case, not
an anomaly, and raising all five to accommodate one of them would grant four
files budget they never asked for. The key names deliberately match the
`category` values in §5, so a lesson routed to `process:scope` and a budget
raised for `process:scope` are written the same way.

**Why a separate file rather than keys in `CONFIG.md`.** Three options were
considered:

| Option                                               | Rejected because                                                                                                                                       |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Budget keys exempt from `CONFIG.md`'s own line count | §6 rule 1 says a line is any line, no exemptions, because exemptions get gamed. This would be the first one, written into the contract by the contract |
| Raise `CONFIG.md`'s budget to fit them               | A file whose budget keys crowd out its actual config is absurd, and 10 lines is tight on purpose                                                       |
| **A separate file read only by `/feedback`**         | **Chosen**                                                                                                                                             |

Only `/feedback` needs to know a budget. Putting these numbers in `CONFIG.md`
would make `/scope`, `/kickoff`, `/build`, `/verify` and `/review` read, on
every single run, a set of numbers none of them ever uses — which is precisely
the tax §1 exists to prevent. The same reasoning that gave `REVIEW_RULES.md`
(§4.4) to two commands instead of all five applies here at its limit: one
reader, one file, zero cost to everyone else.

**The shipped defaults are deliberately tight**, and raising one is a legitimate
move rather than an admission of failure. A 30-line `REVIEW_RULES.md` is a
starting guess about a repo anvil has not seen; a mature codebase with real
review knowledge may genuinely warrant 60, and saying so in `BUDGETS.md` is a
project making an informed decision. That is different in kind from a file
drifting upward because nobody wanted to delete anything.

**When a file is full, drop stale lines first and raise the ceiling second.**
That order matters, and §6's staleness pass is what defines "stale". Reaching
for the ceiling first means never discovering which existing lines had stopped
earning their place, and a file that has never been pruned is where the ceiling
gets raised again six weeks later.

**Direction of travel.** The system should lean toward dropping old lines rather
than growing. A budget that only ever goes up is a signal worth acting on: it
means `/feedback` has stopped distilling and started accumulating, and the fix
is upstream in how lessons are being written, not downstream in the ceiling.

### 4.3 `.anvil/CRITICAL_PATHS.md`

**Purpose.** The flows that must not break, and the cheapest way to check each
one. This file absorbs what would otherwise be a separate `TESTING.md` — one
file, not two, because a second testing file would be read alongside it and
double the cost for no gain.

**Budget.** 40 lines. Default — see §4.2.

**Written by.** `/setup` seeds it from questions; `/feedback` maintains it for
category `path`.

**Format.** One path per line: `<name> — <check>`. The check must be
executable or observable, never "make sure it works".

```markdown
# Critical paths

Login — POST /api/session with seed creds returns 200 and sets cookie
Checkout — cart → pay → confirmation page shows order id
Data export — pnpm test:export passes (guards the CSV column order)
Mobile nav — menu opens at 375px width without layout shift
```

---

### 4.4 `.anvil/REVIEW_RULES.md`

**Purpose.** The checklist of what to look for in code at self-review time.
What to check in the diff — not how a command behaves.

This is the file `RULES.md` was reaching for, scoped correctly. The reason
`RULES.md` was too expensive was never its content, it was that `/scope` and
`/kickoff` paid for review guidance they had no use for. Scoped to the two
commands that read code, the same lines cost a third as much and apply to
something.

**Budget.** 30 lines. Default — see §4.2. One-in-one-out at the limit,
whatever the number.

**Read by.** `/verify` and `/review` only. Zero cost to `/scope`, `/kickoff` and
`/build`.

**Written by.** `/setup` seeds it from human input at setup time; `/feedback`
maintains it for category `review` at two sightings across distinct tickets.

**Format.** One check per line, imperative, stated so a reader can tell whether
a diff passes or fails it.

```markdown
# Review rules

Flag any new public function without a test.
Flag error paths that swallow the error and return a default.
Flag a new dependency where an existing one already does the job.
Flag hardcoded timeouts and retry counts.
Flag SQL built by string concatenation.
```

**Distinction from `process/verify.md`, which will otherwise collect each
other's lines:**

| File                | Holds                                 | Example                                                          |
| ------------------- | ------------------------------------- | ---------------------------------------------------------------- |
| `process/verify.md` | corrections to how the command _runs_ | "Run only the tests touching changed files, not the full suite." |
| `REVIEW_RULES.md`   | what to check _in the diff_           | "Flag any new public function without a test."                   |

The test: if the line would still make sense with no diff in front of you, it is
a `process/verify.md` line. If it only means anything while reading code, it is
a `REVIEW_RULES.md` line. `/feedback` applies that test when routing between
`process:verify` and `review`.

---

### 4.5 `.anvil/process/<command>.md`

**Purpose.** Corrections scoped to one command. Read only when that command
runs. This is the tier most lessons belong in, and — now that no anvil file is
read on every run — the tier most lessons _end_ in.

**Budget.** 20 lines each. Default — see §4.2.

**Written by.** `/feedback` only, for category `process:<command>`, at two
sightings across distinct tickets. `/setup` creates all five, each containing
its title line and nothing else.

**These files ship empty. Do not seed them.** All five look like this on day
one:

```markdown
# Process: scope
```

**Why no seeds** — recorded here because reintroducing them is a natural idea
and it is wrong. A universal lesson that has not been observed _in this repo_ is
still a guess, however plausible. "Slice so one ticket is one PR a human can
review in one sitting" is good advice and it is exactly the kind of line that
belongs here — but until this project has actually produced an oversized PR, it
is anvil assuming rather than anvil knowing.

The asymmetry is the point. An empty file costs nothing and misleads nobody. A
wrong seeded line costs budget _and_ gets trusted, because nothing in the file
distinguishes a shipped guess from a line this repo earned through two
independent sightings. A guess that occupies budget and gets believed is worse
than an absence.

If a lesson really is universal, it will be observed here within a few tickets
and promoted on evidence, at which point it is no longer a guess. The cost of
waiting is a few tickets. The cost of guessing wrong is a line that shapes every
run of that command until someone notices.

A file still empty after a dozen or so tickets is evidence that command does not
need one; delete it. It costs nothing while empty, so there is no urgency —
this is housekeeping, not a rule.

**Format.** One imperative line each. No headings beyond the title, no
rationale, no "prefer" or "consider" or "try to".

One file per command: `scope.md`, `kickoff.md`, `build.md`, `verify.md`,
`review.md`.

### 4.6 `.anvil/feedback/human.jsonl` and `.anvil/feedback/self.jsonl`

**Purpose.** Append-only record of every correction and every stall, in the
moment it happened. This is raw material, not context. Only `/feedback` and
`/research` (§4.11) read them, and they have no size budget — they are the
evidence base, and throwing evidence away is how the system stops learning.

Two files, **one schema**, split by who noticed:

| File          | Holds                                        | `correction`                                                             |
| ------------- | -------------------------------------------- | ------------------------------------------------------------------------ |
| `human.jsonl` | corrections a person made                    | nullable — a person can flag something without saying what to do instead |
| `self.jsonl`  | stalls and guesses the model observed itself | **always** `null`                                                        |

There is no `source` field. The filename carries it, which is why the split is
worth having at all: a field you have to grep for is worse than a file you can
`cat`.

**Why split.** "Show me only what I actually corrected" is a question worth
being able to answer with `cat feedback/human.jsonl` and no tooling. The two
kinds of entry also carry genuinely different weight when reviewing — a person
stopping to correct something is a stronger signal than the model noticing it
read four files too many — and that difference is easier to hold onto when the
files are separate than when it is one field among ten.

**Do not split further.** Splitting _by command_ breaks cross-command routing,
which is the case that matters most: `fb-0046` below is captured by `/build` and
routed to `/kickoff`, and in a per-command log it would sit in a `/build` file
that `/kickoff` never benefits from. Two files, split one way, is the whole
allowance.

#### The counting rule

> **`/feedback` reads BOTH files and counts sightings of a fingerprint ACROSS
> both. A fingerprint seen once by a human and once by the model is **two**
> sightings, not one each.**

This is a hard rule, not a note, and it is the entire risk the split carries.
Two files invite two counters. With separate counters, a lesson that alternates
between human-caught and self-caught never reaches its threshold — and that
alternating case is the _strongest_ evidence available, because it means the
model independently hit what a person had already flagged. Counting it as one
each would throw away the best signal in the system.

Anything `/feedback` does per-fingerprint — counting, promoting, marking
`promoted` — operates on the union of the two files. The split is a storage
decision and must never become a routing decision.

**Budget.** None, on either file. Never read at runtime by `/scope`,
`/kickoff`, `/build`, `/verify` or `/review`.

**Written by.** Every command, appending as corrections and stalls happen, to
whichever of the two files matches who noticed. A command must flush its entries
before it exits, because `/clear` runs between commands and unflushed context is
gone.

**Format.** JSON Lines — one object per line, so git diffs cleanly and appends
never conflict. The schema below is **identical in both files**.

| Field           | Type           | Meaning                                                    |
| --------------- | -------------- | ---------------------------------------------------------- |
| `id`            | string         | `fb-NNNN` — monotonic **across both files**, see below     |
| `ts`            | string         | ISO 8601 UTC                                               |
| `ticket`        | string \| null | ticket dir name, null if outside a ticket                  |
| `command`       | string         | which command captured it                                  |
| `category`      | string         | routing key — see §5                                       |
| `fingerprint`   | string         | short kebab key identifying the _lesson_, not the instance |
| `observed`      | string         | what Claude did                                            |
| `correction`    | string \| null | what the user said instead; always `null` in `self.jsonl`  |
| `proposed_line` | string \| null | the one-line constraint this would become                  |
| `status`        | string         | `open` \| `promoted` \| `parked` \| `dropped`              |

**Ids are one sequence, not two.** `fb-NNNN` is monotonic across both files —
the next id is `max(both) + 1`. Two per-file sequences would collide, and
`unrouted.md` (§4.7) references entries by id while drawing from both files, so
a collision there means an ambiguous pointer into the evidence base.

`correction` is nullable in `human.jsonl` because a person can flag something
without saying what to do instead — "this is wrong" is a real entry, and forcing
a fabricated correction into it would be worse than a null. In `self.jsonl` it
is always `null`: nobody corrected anything. `observed` and `proposed_line` are
exactly as useful either way, and being in one of these two files is what makes
an entry fingerprintable at all.

A `self.jsonl` entry does not face a lower bar. It still passes the admission
test in §1, and its fingerprint still has to hit the threshold in §5 — counted
across both files — before it reaches a context file.

**Concrete example.** Three entries in `human.jsonl`: a lesson at one sighting,
the same lesson from a different ticket, and an uncategorisable correction.

<!-- prettier-ignore -->
```jsonl
{"id":"fb-0031","ts":"2026-08-07T09:41:02Z","ticket":"0007-add-auth-guard","command":"scope","category":"process:scope","fingerprint":"ac-written-as-implementation","observed":"Wrote acceptance criteria as 'add middleware to src/auth.ts that checks the session cookie'.","correction":"A/C should say what a user can observe, not which file to touch. Should have been 'a request without a valid session gets a 401'.","proposed_line":"Write acceptance criteria as observable outcomes, never as implementation steps.","status":"open"}
{"id":"fb-0044","ts":"2026-08-11T14:02:55Z","ticket":"0009-export-csv","command":"scope","category":"process:scope","fingerprint":"ac-written-as-implementation","observed":"A/C listed the columns to add to the CSV writer function.","correction":"Same problem as last time — describe the downloaded file, not the writer.","proposed_line":"Write acceptance criteria as observable outcomes, never as implementation steps.","status":"open"}
{"id":"fb-0045","ts":"2026-08-11T16:20:10Z","ticket":"0009-export-csv","command":"verify","category":"unrouted","fingerprint":"verify-ran-full-suite","observed":"Ran the entire test suite to check one CSV change; took 11 minutes.","correction":"Should have run only the export tests. But I don't know if that's a rule, a map entry, or just this repo being slow.","proposed_line":null,"status":"open"}
```

And one entry in `self.jsonl` — nobody corrected it, so `correction` is `null`.
Note its id: `fb-0046` follows `fb-0045` from the _other_ file, because the
sequence is shared.

<!-- prettier-ignore -->
```jsonl
{"id":"fb-0046","ts":"2026-08-12T10:07:31Z","ticket":"0009-export-csv","command":"build","category":"process:kickoff","fingerprint":"plan-omits-schema-change","observed":"Stalled at PLAN.md step 3. It said 'persist the export settings' without saying whether that meant a new column on exports or a new table. Read four files and the last two migrations, then guessed a new column.","correction":null,"proposed_line":"When a step changes the database, PLAN.md must name the table and the columns.","status":"open"}
```

At the next `/feedback` run, `ac-written-as-implementation` has two sightings
across two distinct tickets, which clears the command tier threshold. It is
promoted into `process/scope.md` as its `proposed_line`, and both entries flip
to `promoted`. It is **not** eligible for a `CLAUDE.md` proposal — that needs
three, and even then anvil only proposes.

`verify-ran-full-suite` has no route, so it moves to `unrouted.md` and its
status becomes `parked`.

`plan-omits-schema-change` is the shape that matters most for `/build`: captured
by one skill, routed to a different one. It stays `open` at one sighting; if
`/build` stalls the same way on another ticket, it hits two and lands in
`process/kickoff.md`, and `/kickoff` stops producing plans with that hole. Note
that `command` and `category` differ — `command` records who saw it, `category`
records who should change. They are frequently not the same skill.

**Worked example: one fingerprint across both files.** This is the case the
counting rule exists for. A person catches it once, and on a later ticket the
model catches the same thing itself.

In `human.jsonl`:

<!-- prettier-ignore -->
```jsonl
{"id":"fb-0058","ts":"2026-08-18T11:14:09Z","ticket":"0011-saved-filters","command":"kickoff","category":"process:kickoff","fingerprint":"context-omits-feature-flag","observed":"CONTEXT.md listed the six files the change touches but did not mention that the whole path is behind the `saved_filters` flag, which is off by default.","correction":"Say which flag gates it. I nearly tested with the flag off and reported it broken.","proposed_line":"CONTEXT.md must name any feature flag gating the code under change.","status":"open"}
```

In `self.jsonl`, two tickets later:

<!-- prettier-ignore -->
```jsonl
{"id":"fb-0063","ts":"2026-08-25T09:52:40Z","ticket":"0013-search-ranking","command":"build","category":"process:kickoff","fingerprint":"context-omits-feature-flag","observed":"Implemented the ranking change, tests passed, then saw no behaviour change in the app. The path is behind `beta_search`, which CONTEXT.md did not mention. Found it by grepping the flag registry.","correction":null,"proposed_line":"CONTEXT.md must name any feature flag gating the code under change.","status":"open"}
```

At the next `/feedback` run, `context-omits-feature-flag` has **two sightings**
— one per file, across two distinct tickets — which clears the command tier
threshold. The `proposed_line` is promoted into `process/kickoff.md` and **both**
entries flip to `promoted`, in both files.

Counted per file it would be one and one, sitting below the threshold forever,
and the lesson would never land despite being the best-evidenced thing in the
log: a person flagged it, and then the model hit it independently without having
seen the earlier entry. That is exactly the signal worth acting on, so it must
not be the one the file layout discards.

**Future cost: rotation.** `/feedback` parses both files in full on every run.
Somewhere around **2000 entries** that stops being free and rotation becomes
worth considering — **the same threshold applies to each file independently**,
most likely keeping `open` entries in place and moving `promoted` or `dropped`
ones to a dated archive per file, since those are the ones `/feedback` no longer
needs to re-read. Any rotation scheme must preserve cross-file fingerprint
counting for entries still `open`. Not built now, because premature
rotation would risk the fingerprint counting that everything else depends on.
Recorded so it is a known future cost rather than a surprise slowdown.

### 4.7 `.anvil/feedback/unrouted.md`

**Purpose.** The visible pile of corrections `/feedback` could not route. This
is not a rubbish bin — it is the evidence for what the next category should be,
and for where the routing table is wrong. Discarding these is how you stay
blind to your own design errors.

**Budget.** None, but `/feedback` prints the count on every run, and a count
above 10 is a prompt to review the categories.

**Read by.** `/feedback` and `/research` (§4.11). It is `/research`'s primary
input — the pile is the question set.

**Written by.** `/feedback`.

**Format.** One entry per bullet, newest last, carrying the `fb-NNNN` id so the
full record is recoverable.

This file draws from **both** logs, which is why ids are one sequence across
them (§4.6). A bare `fb-0045` here has to resolve to exactly one entry; two
per-file sequences would make it ambiguous which log to look in.

```markdown
# Unrouted

- `fb-0045` verify ran the full suite for a one-file change. Unclear whether
  this is a rule, a map entry, or repo slowness. (2026-08-11)
- `fb-0052` asked for a design token that has no source of truth in this repo.
  Possibly a CONFIG entry, possibly a missing design system. (2026-08-14)
```

### 4.8 `.anvil/tickets/<id>/`

**Ticket id format.** `NNNN-short-kebab-slug`, e.g. `0007-add-auth-guard`.
`/scope` mints the number as `max(existing) + 1` — no counter file, no state to
corrupt. If `CONFIG.md` sets `tracker` to anything other than `local`, `/scope`
asks for the external id instead and uses `<external-id>-slug`.

| File                       | Written by | Budget   | Format                                                                          |
| -------------------------- | ---------- | -------- | ------------------------------------------------------------------------------- |
| `TICKET.md` **(optional)** | `/scope`   | 40 lines | Problem, Scope, Out of scope, Acceptance criteria (numbered, observable)        |
| `CONTEXT.md`               | `/kickoff` | 40 lines | Files that matter and why; ticket-tier lessons; nothing inferable from the code |
| `PLAN.md`                  | `/kickoff` | 60 lines | Numbered steps, each one a checkable change                                     |
| `TEST_CASES.md`            | `/kickoff` | 40 lines | One case per line: `<given> → <expected>`                                       |
| `VERIFY.md`                | `/verify`  | none     | See §4.9                                                                        |

**`TICKET.md` is present** under `tracker: local` (mode 1) and under an external
tracker with no integration (mode 3, as a labelled mirror). It is **absent**
under a working external integration (mode 2), where the tracker holds the body
and the directory contains only the `/kickoff` files. Full detail below — but do
not skim past this line, because a skill that assumes the file exists is wrong
in one of the three modes.

The ticket body and the `/kickoff` trio sit behind human approval gates. A
command must stop and wait for an explicit approval from the user; it must not
write the next stage's files in the same run.

`/build` writes no file of its own. Its output is code, plus entries in
the feedback logs under `command: "build"` — mostly `self.jsonl`, since a stall
is self-observed.

**`/build`'s justification.** `/build` earns its place if entries with
`command: "build"` produce lessons that improve `/kickoff` — the
`plan-omits-schema-change` shape in §4.6. If after three tickets the logs hold
no build entries, `/build` is doing nothing that reading `PLAN.md` does not
already do, and it should be deleted with `PLAN.md` becoming the interface.

### Ticket source of truth

`TICKET.md` is not unconditional. `CONFIG.md`'s `tracker:` key decides where the
ticket body lives, in three modes:

| `tracker:`                    | Ticket body lives in | `TICKET.md` written?                         |
| ----------------------------- | -------------------- | -------------------------------------------- |
| `local`                       | `TICKET.md`          | Yes — it **is** the ticket                   |
| external, integration working | the tracker          | **No** — dir holds only the `/kickoff` files |
| external, no integration      | the tracker          | Yes, as a labelled **mirror**                |

**Mode 1 — `tracker: local`.** `/scope` authors `TICKET.md` and it is the source
of truth. Nothing else holds the ticket body.

**Mode 2 — external with a working integration.** The tracker holds the body and
anvil does not copy it. `/kickoff` fetches it. `.anvil/tickets/<id>/` contains
`CONTEXT.md`, `PLAN.md`, `TEST_CASES.md` and `VERIFY.md` only. Writing a local
copy here would be a second source of truth that nothing keeps in step.

**Mode 3 — external with no integration.** Anvil cannot reach the tracker, so
`/scope` drafts the ticket, the user pastes it into the tracker by hand, and the
draft persists locally as a mirror. Line 1 is the literal word `MIRROR` and line
2 carries the external id:

```markdown
MIRROR
external: PROJ-482
updated: 2026-08-12

# Problem

...
```

> **Governing rule: exactly one source of truth per repo, named in `CONFIG.md`, and
> a mirror is always labelled as one.**

Without the label, a local `TICKET.md` and an external ticket drift apart and
nothing on disk says which one `/kickoff` actually read. The `MIRROR` line is
what lets a human — and `/review` — know that the local file may be stale and
the tracker wins. A mirror is never edited by anvil after `/scope` writes it; if
the tracker changes, the user re-pastes.

### 4.9 `.anvil/tickets/<id>/VERIFY.md`

**Purpose.** The record of what `/verify` actually checked and what it saw.
Written once per `/verify` run and overwritten on re-run — it reflects the
current state of the ticket, not its history. The history is in git.

This is the artifact a human reviewer wants to read, and in practice the only
one they will. It is the difference between "verified" as a claim and
"verified" as something you can check.

**Budget.** None, but one line per case and no prose. The file grows with the
number of cases, which is the only thing it is allowed to grow with. A `VERIFY.md`
containing paragraphs is a bug.

**Written by.** `/verify` only.

**Read by.** Nobody. No skill reads `VERIFY.md` — not `/review`, not `/feedback`.
It is committed rather than ephemeral, because a reviewer opening the PR a week
later needs it, but it is written for humans and carries no runtime cost.

**Format.** One line per case:

```
<case> — PASS|FAIL|COULD NOT CHECK — <evidence>
```

Evidence is a command and what it returned, never an assertion. "Works
correctly" is not evidence. "The login flow was tested" is not evidence. If
there is no command and no observation, the verdict is `COULD NOT CHECK`, and
saying so is always better than a `PASS` nobody witnessed.

```markdown
# Verify — 0009-export-csv

Empty cart exports header row only — PASS — `pnpm vitest run export` 14 passed
Column order matches the spec — PASS — `pnpm vitest run export.order` 3 passed, guards the fixture
Export of 10k rows completes under 5s — FAIL — `pnpm vitest run export.perf` timed out at 30s, 1 failed
Login — PASS — `curl -si localhost:3000/api/session -d @seed.json` returned 200, Set-Cookie present
Checkout — COULD NOT CHECK — CONFIG.md has `smoke: none`, no browser driver available; run manually: cart → pay → confirmation shows order id
Mobile nav at 375px — COULD NOT CHECK — same, `smoke: none`
```

Every `COULD NOT CHECK` line states why, and where the cause is `smoke: none`
the line carries the manual steps so the human can finish the job. That is the
degradation path from §4.1 landing in a file: `/verify` never fails the run for
want of a smoke driver, and never converts an unchecked case into a pass.

### 4.10 Deleted: `RULES.md`

Recorded so nobody reintroduces it from first principles.

Anvil used to own a `RULES.md`: 30 lines of global constraints, read on every
run, the most expensive file in the system. It was deleted because **no line was
ever found that met all three of its requirements at once**:

1. repo-specific — otherwise it is a general coding rule and belongs nowhere,
2. spanning more than one anvil command — otherwise it is a `process/*.md` line,
3. not already a `CLAUDE.md` fact — otherwise anvil is paying a second time for
   something every tool in the repo already reads.

Every candidate failed on 3. "Never edit files under `src/generated/`", "run
lint before proposing a commit", "migrations are forward-only" — each is true
whether or not anvil is running, so stating it in an anvil file duplicates a
`CLAUDE.md` line and creates two places for the same constraint to drift apart.
The version anvil could actually use — what to look for in a diff — was not
global at all; it was needed by two commands, and is now `REVIEW_RULES.md`
(§4.4) at a third of the cost.

**How it comes back.** With evidence, not by argument. If `unrouted.md`
accumulates entries that are repo-specific, cross-command, and genuinely not
`CLAUDE.md` material, those entries are the case for reinstating the file, and
they will name its budget by their number. Until then the global tier stays a
proposal to `CLAUDE.md` (§5, category `claude-md`) and anvil owns no file that
is read on every run.

### 4.11 `/research` — the outward channel

`/research` is the one skill in §0's tree that specifies no file of its own. It
is listed here because every other skill is, and an omission would read as an
oversight.

**Purpose.** Turn the patterns anvil could not resolve into a question aimed
outside the repo.

The distinction from `/feedback` is the whole justification for the skill, and
it is a distinction of direction rather than of mechanism:

| Skill       | Evidence         | Acts on           | Output                    |
| ----------- | ---------------- | ----------------- | ------------------------- |
| `/feedback` | this repo's logs | this repo's files | promoted lines, evictions |
| `/research` | this repo's logs | nothing on disk   | a prompt for someone else |

`/feedback` improves **this** repo's files from **this** repo's evidence.
`/research` turns unresolved patterns into a question for outside
investigation, and is the channel by which anvil learns from repos its author
will never see. A repo that keeps parking the same shape of correction knows
something about the routing table that anvil's author cannot know from here.

**Reads.** `feedback/unrouted.md` and both logs (§4.6, §4.7). Nothing else. It
reads no context file, so its cost to the numbers in §3 is zero.

**Writes.** Nothing. No context file, no ticket, no log entry, no `unrouted.md`
edit. It emits a prompt to the session and stops.

That is not an accident of scope — it is what keeps `/review`'s one-writer
invariant intact while adding an eighth skill that reads the same evidence base
`/feedback` does. A skill that both read the logs and edited context files
would be a second writer under a different name.

**The prompt.** One research question, the parked entries that motivate it
quoted by `fb-NNNN` id, and what an answer would change. Two destinations, and
the skill names both rather than assuming one:

1. **Run it yourself** — paste it into Claude research or parallel.ai, and act
   on the answer in your own repo.
2. **Send it upstream** — open an issue on `anvil-skills` from the research
   issue template. The template is the entire contribution infrastructure;
   there is no submission endpoint, no telemetry, and nothing leaves the repo
   unless a human pastes it.

Upstream is the interesting one. It is the only path by which evidence from a
repo the author will never see reaches the routing table in §5, and it costs a
GitHub issue template to build.

**When it is worth running.** `unrouted.md` past the count §4.7 names, or the
same fingerprint parked repeatedly across tickets. Running it against an empty
pile produces a question with no evidence behind it, which is the same error as
seeding a `process/*.md` from a guess (§4.5).

**`/research`'s justification**, in the same shape as `/build`'s (§4.8). It
earns its place if the prompts it emits are acted on — run by the user, or
opened as an issue here. If none ever is, `/research` is a skill description
charged to every session for nothing and it should be deleted rather than kept
for tidiness.

## 5. Categories and routing

`category` is the field `/feedback` routes on. The set is closed. If a
correction does not fit, it is `unrouted` — inventing a category on the fly
defeats the point of having a table.

| Category          | Destination                            | Threshold                      |
| ----------------- | -------------------------------------- | ------------------------------ |
| `claude-md`       | **proposed** to the repo's `CLAUDE.md` | 3 distinct tickets             |
| `config`          | `CONFIG.md`                            | 1 — it is a fact, not a lesson |
| `path`            | `CRITICAL_PATHS.md`                    | 1 — same                       |
| `review`          | `REVIEW_RULES.md`                      | 2 distinct tickets             |
| `process:scope`   | `process/scope.md`                     | 2 distinct tickets             |
| `process:kickoff` | `process/kickoff.md`                   | 2 distinct tickets             |
| `process:build`   | `process/build.md`                     | 2 distinct tickets             |
| `process:verify`  | `process/verify.md`                    | 2 distinct tickets             |
| `process:review`  | `process/review.md`                    | 2 distinct tickets             |
| `ticket`          | that ticket's `CONTEXT.md`             | 1, written at capture time     |
| `unrouted`        | `feedback/unrouted.md`                 | n/a                            |

`config` and `path` are facts about the repo rather than lessons about
behaviour, so they route on first sighting. Everything behavioural needs
repetition.

**`claude-md` writes nothing.** It is the only category with no anvil
destination. At three sightings `/feedback` prints a proposed one-line addition
and the reason, and stops. The human edits `CLAUDE.md` or does not. Entries stay
`open` until the human says which — anvil must not mark its own proposal
`promoted`, because it does not know whether it was accepted.

That asymmetry is deliberate. `CLAUDE.md` is read by every tool in the repo and
owned by the people working in it. Anvil earning the right to _suggest_ a line
after three independent sightings is reasonable; anvil silently editing the
file every session reads from is not.

**The one thing that closes an `open` proposal is the line turning up in
`CLAUDE.md`.** That is the human's acceptance, on disk, and it is the only
evidence of acceptance anvil ever gets — nobody comes back to tell `/feedback`
what they decided. When the staleness pass sees it (§6, trigger 2) it removes
the now-duplicated anvil-side line and flips the proposal to `promoted` in the
same pass. The rule above is unchanged: anvil does not mark a proposal
`promoted` on its own say-so, it marks one `promoted` on seeing the accepted
line.

## 6. Budget enforcement

The mechanism is fixed. The number it enforces comes from `BUDGETS.md` (§4.2)
if the project set one, and from the §4 default otherwise. `/feedback` resolves
the number first, then applies the rule below without variation.

The rule `/feedback` implements:

1. A line is any line in the file, including headings and blanks. No
   exemptions — exemptions get gamed.
2. Check with `wc -l < <file>` against the resolved budget.
3. If adding a line would exceed the budget, `/feedback` must name the line it
   is evicting and state why the new line is worth more. Both facts are appended
   to `self.jsonl` as an entry with `command: "feedback"` and
   `category: "unrouted"` carrying the evicted text, so nothing vanishes
   silently.
4. If it cannot make the file fit — because no existing line is weaker than the
   new one — `/feedback` **fails hard**, reports the conflict, and presents
   **both** ways out:
   - evict a specific named line, or
   - raise this file's budget in `BUDGETS.md`.

   It does neither itself. It does not ship an over-budget file, it does not
   silently drop the new lesson, and — this is the part that matters — **it
   never edits a budget key.**

There are no exceptions to step 3. Every line in a context file was promoted on
evidence, so every eviction is a real trade between two things that both earned
their place.

**Why `/feedback` cannot raise a budget itself.** Raising a ceiling is a human
decision by definition: the entire meaning of the act is that someone looked at
the trade and chose to pay more. A tool that raises its own ceiling when it finds
the ceiling inconvenient has not made that decision, it has removed it — and it
would do so at exactly the moment the ranking question was about to be asked. The
hard failure _is_ the mechanism. Letting `/feedback` resolve it alone deletes
the only point in the system where someone is forced to say which of two
constraints actually matters.

That is a question worth stopping for, and stopping is the whole feature.

### The staleness pass

Budget pressure is not the only reason a line should leave a context file. It is
just the only one that announces itself. A line that has quietly stopped earning
its place is charged to every run of its command forever, and nothing about a
full file is what makes that wrong.

So `/feedback` runs a staleness pass on **every** run, not only when a file is
at its ceiling. Three triggers, and they do not have the same authority.

**Trigger 1 — budget pressure.** Unchanged, and specified by steps 1–4 above.
One-in-one-out at the ceiling, the evicted line named and justified, hard fail
when nothing existing is weaker than the new line.

**Trigger 2 — duplication.** `/feedback` reads the repo's `CLAUDE.md` and checks
whether the substance of any context-file line now appears there. If it does,
the anvil-side line is **removed automatically** and the removal logged.

Nothing is lost when this fires: the constraint still holds, it is just stated
once instead of twice. This is the exact case a `claude-md` proposal creates —
the proposal is accepted, the human adds the line to `CLAUDE.md`, and the
`process/*.md` or `REVIEW_RULES.md` line that generated it is still sitting
there being paid for on every run of its command. Two statements of one
constraint is also how the two drift apart, which is the failure §4.10 deleted
an entire file to avoid.

> **When trigger 2 fires on a line whose fingerprint has an open `claude-md`
> proposal, that proposal flips to `promoted` in the same pass.**

Without that, the two halves of the same event never meet. §5 leaves a
`claude-md` proposal `open` because anvil cannot tell whether the human accepted
it — but a line appearing in `CLAUDE.md` **is** the human having accepted it,
observed rather than assumed. Left un-flipped, the proposal stays `open`
forever and `/feedback` re-proposes it on the next run against a `CLAUDE.md`
that already contains it, while the line it came from has just been removed.
Flipping it in the same pass is not anvil marking its own homework; it is anvil
recording a decision it can see was made.

The rule is stated in terms of the fingerprint rather than of run order, which
is why nothing else here specifies an ordering. The removal and the flip are two
effects of one fingerprint match, applied in one pass.

**Trigger 3 — obsolescence.** A line promoted more than `stale_after` tickets
ago whose fingerprint has not been seen since is **presented for review**, and
never removed automatically. `/feedback` names the line, says when it was
promoted and how long since the fingerprint last appeared, and stops there. The
user drops it or keeps it.

`stale_after` resolves the same way every other number in this document does:
from `BUDGETS.md` if the project set one, from the §4.2 default of **20**
otherwise. It is a shipped guess and a project may override it — a repo moving
fast enough to want the question after five tickets should not wait twenty for
it.

**The asymmetry between 2 and 3 is deliberate.** Duplication is provable —
`/feedback` reads the context file and `CLAUDE.md` and sees the same constraint
stated twice — and being wrong about it costs nothing, because the constraint
survives either way.
Obsolescence is a judgment call, and the evidence for it is an absence. A
fingerprint going quiet has two readings that look identical in the logs: the
lesson is dead weight because Claude is now good enough at that pattern, or the
line is working and the silence is the line doing its job. The second is common
and a tool cannot tell it from the first. Removing on that guess would be the
same error as seeding a file from a guess (§4.5) — a change to what every run of
a command sees, made on evidence that does not support it.

**Age comes from the logs, not from the files.** Do not date-stamp lines in
context files, and do not build citation tracking. Both are the obvious answer
and both are wrong: a date stamp spends budget on metadata in a file whose whole
constraint is line count, and citation tracking is machinery for a question
already answered elsewhere.

Every promoted line has at least one log entry behind it carrying `ts`, `ticket`
and `status: promoted` (§4.6). `/feedback` already reads both logs in full on
every run, so it reconstructs when a line was promoted and when its fingerprint
was last seen at **zero additional cost** to anything read at runtime. The
context files stay pure constraint. The logs already hold the history.

**Every removal is logged.** Triggers 2 and 3 append to `self.jsonl` exactly as
trigger 1 does under step 3 — an entry with `command: "feedback"` and
`category: "unrouted"`, carrying the removed text and naming which trigger
fired. A trigger-3 removal is logged when the user accepts it, not when it is
presented.

This is what makes "no feedback is lost" true, and it is worth being precise
about which half of the system the claim applies to: **the context files are a
cache and the logs are the permanent record.** A line leaving a context file is
a line no longer being paid for on every run. It is not a line deleted from the
system, and anything evicted can be found, re-argued and re-promoted from the
log it was written to.

## 7. Open questions

Deliberately unresolved. Each is parked until evidence arrives.

- **PR template.** Whether `/verify` should update the repo's PR template with a
  smoke-test section, post a PR comment, or do neither. Touching a shared
  template is invasive for a tool that claims to work in any repo. Parked until
  `/verify` exists (M5) and there is something real to report.
- **MCP smoke tests.** `smoke:` in `CONFIG.md` names an MCP server, but MCP may be
  absent in any given session. `/verify` must degrade to a manual checklist
  rather than fail. Confirmed at M5.
- **Ticket ids.** Defaulting to local slugs. If `tracker` ends up always
  pointing at a real backlog, the local path is dead weight and should go. See
  the worktree collision noted under `CONFIG.md`.
- **Tracker modes 2 and 3 are untested by the roadmap.** `anvil-skills`, `site`
  and `dodgeball` are all `tracker: local`, so M0–M7 exercise mode 1 only. The
  mirror format and the no-local-copy rule are specified but unproven. Either a
  milestone gains a repo with a real tracker, or the contract should say the
  external modes are provisional. Not resolved here — it needs a decision about
  which repo, and there may not be one.
- **~~`MAP.md` versus an existing `CLAUDE.md`.~~ Decided.** `CLAUDE.md` wins,
  and anvil does not duplicate it. `MAP.md` is now `CONFIG.md` (§4.1) and holds

  that created the overlap are gone from it, and the always-read file that

  repo, and the answer is either an explicit `manual:` prefix or an honest
  admission that anvil does not cover taste.

## 8. Does this repo ship its own `.anvil/`?

**Decision: yes, it ships.** Anvil's claim is that a process improves by being
corrected, and a real `feedback/human.jsonl` with real entries and a real
`unrouted.md` is the only honest evidence for that. A user can read what anvil
actually learned rather than take the README's word for it. It is also the
dogfooding surface — M3 depends on this repo running anvil on itself.

Two conditions, both mandatory:

1. **The path rule in §0 holds everywhere.** Shipping `.anvil/` into
   `~/.claude/plugins/cache/` is only safe because no skill can ever resolve a
   bare `.anvil/`. If the path rule is violated, this decision becomes a bug
   that reads the wrong project's rules, so the two are a package.
2. **The README says so explicitly.** An unexplained `.anvil/` inside an
   installed plugin looks like packaging sloppiness. The README states that it
   is this project's own working history, that it is deliberate, and that it is
   never read when anvil runs in another repo.

If either condition lapses, `.anvil/` moves to a `docs/example-anvil/` snapshot
instead. There is no manifest-level exclusion mechanism to reach for — the
directory either ships or it is not in the published tree, so relocating it is
the only lever.
